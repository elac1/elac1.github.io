## 广播电台 vs 打电话

把 ROS 的通信想象成现实生活：

- **话题（Topic）= 广播电台**——一个节点发，多个节点听，不需要知道谁在听，也不需要对方回应
- **服务（Service）= 打电话**——一问一答，调用方必须等对方回一个结果

## 什么时候用话题？

话题适合**持续、单向、可能有多个接收者**的数据：

- 激光雷达每秒扫描 10 次 → `scan` 话题
- 机器人的实时位置 → `odom` 话题
- 摄像头画面 → `image` 话题

特点：**发了就不管**，丢一两条没关系，频率高。

## 什么时候用服务？

服务适合**需要结果、可能要等待、不常发生**的请求：

- "请帮我导航到 A 点" → 导航服务返回"已开始"
- "把机械臂转到这个角度" → 返回"已完成"或"失败"
- 查询机器人当前状态 → 返回一个结构体

特点：**必须有回应**，调用方会阻塞直到收到结果（或超时）。

## 代码对比

```python
# 话题：发了就走
pub.publish(msg)
# 不需要等谁响应

# 服务：必须等结果
response = client.call(request)
# response 里有具体的成功/失败信息
```

## 一个容易踩的坑

不要用话题来做"请求-响应"模式。比如你想让另一个节点做一件事然后告诉你结果，用话题实现会很别扭——你得开一个"请求话题"和一个"响应话题"，还要匹配 request_id。**这时候直接用服务**。

反过来，也不要用服务发高频数据。如果你每秒要发 50 次传感器数据，每次都同步等待响应，整个系统会卡成壳。
